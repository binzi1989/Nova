# NOVA 响应式运行体验设计（preview.17）

## 问题

当前界面把“距离最后一段数据的秒数”直接展示给用户，但这不能说明任务是否卡死，也不能帮助用户做出决定。长推理、工具执行、网络断流和宿主异常被混成了同一种等待状态。

## 新原则

1. 不显示不断增长的焦虑倒计时。
2. 只展示可被系统证实的阶段，不伪造百分比。
3. NOVA 先自动诊断和恢复，确实需要决定时再打扰用户。
4. 停止、重试和切换模型都保留上下文、附件、检查点与已有产出。
5. 长任务允许进入后台，完成后用桌面通知提醒。

## 六态运行模型

| 状态 | 用户看到 | 系统行为 |
| --- | --- | --- |
| PREPARING | 正在理解目标 | 编译上下文、检查附件与权限 |
| WORKING | 正在分析 / 正在调用工具 | 按真实 Runtime 事件展示当前阶段 |
| COMPOSING | 正在整理结果 | 接收或组装模型输出 |
| VERIFYING | 正在检查交付物 | 验证文件、格式和完成条件 |
| RECOVERING | 连接短暂中断，正在恢复 | 检查宿主、模型请求和流连接，有限次数恢复 |
| NEEDS_ATTENTION | 需要你决定下一步 | 仅在自动恢复失败后显示选择 |

`模型沉默` 不再是一个用户状态。它只是运行诊断的一个信号。

## 页面体验

### 默认状态

回答下方只显示一条轻量状态：

> 正在整理结果…

左侧为柔和脉冲点，右侧提供“后台继续”。不展示秒数。

### 展开详情

用户点击状态条后，可以看到：

- 当前阶段：深度分析 / 工具执行 / 结果整理 / 本地验证
- 当前执行者：NOVA 或具体子 Agent
- 最近一次真实进展
- 已产生的临时文件或检查点

### 自动恢复

- 20 秒无模型数据：后台健康检查，不打扰用户。
- 流连接异常：显示“连接短暂中断，正在恢复”，自动恢复最多两次。
- 请求仍被提供商接受：保持“仍在处理中”，不重复发送请求。
- 宿主无响应或恢复失败：进入 NEEDS_ATTENTION。

### 需要用户决定时

只提供三个含义明确的操作：

1. **继续后台等待**：任务继续运行，完成后桌面通知。
2. **从检查点恢复**：不重发已完成步骤，只恢复未完成阶段。
3. **停止并保留结果**：保留上下文、附件、流式文本和已落盘文件。

如已连接其他模型，可在“从检查点恢复”内选择切换模型，不单独堆一个按钮。

## Runtime 协议补全

每个运行请求应具有：

- `requestId`
- `taskId`
- `phase`
- `providerStatus`
- `lastModelChunkAt`
- `lastRuntimeEventAt`
- `checkpointId`
- `recoverable`
- `recoveryAttempt`

宿主每 5 秒发送轻量心跳。心跳不代表模型有输出，但可以区分“宿主仍工作”和“宿主失联”。恢复必须沿用原任务和检查点，禁止创建重复任务或重复扣除已完成阶段的预算。

## 文案规范

避免：

- 模型已 74 秒没有返回新数据
- 可能卡住了
- 停止后重试

使用：

- 正在分析资料
- 正在等待模型完成较长推理
- 连接短暂中断，NOVA 正在恢复
- 自动恢复未成功，需要你决定下一步
- 已保留本轮内容，可以从检查点继续

## 验收标准

1. 正常长推理 2 分钟内不出现错误式提示或不断增长的秒数。
2. 断开流连接后，界面 3 秒内进入 RECOVERING，并自动尝试恢复。
3. 恢复不会重复创建任务、重复执行已完成工具或丢失附件。
4. 点击“停止并保留结果”后，当前流式内容和文件仍可查看。
5. 长任务可以后台运行，完成或失败时发送桌面通知。
6. 用户在主界面始终只看到一个主要状态和一个主要动作。
